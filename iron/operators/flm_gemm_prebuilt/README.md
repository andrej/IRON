# FLMGEMMPrebuilt — the shipped FastFlowLM `mm` overlay

Runs FastFlowLM's `mm.xclbin` unmodified, so that it can be measured against
[`FLMGEMM`](../flm_gemm), the IRON port of it, and against the general
[`GEMM`](../gemm), at the same shapes in the same CI run.

The overlay exists only as a binary. This operator supplies the other half of
a dispatch: the runtime parameters and the shim DMA transfers. Every core
program, memtile buffer and stream-switch route comes from the xclbin.

```python
op = FLMGEMMPrebuilt(M=M, K=K, N=N, context=ctx)
op.compile().get_callable()(A, op.pack_B(B), C_out)
```

On NPU2 (aie2p) only: the overlay occupies a 4x8 grid.

## Where the xclbin comes from

`op.py` pins a FastFlowLM commit and the file's SHA-256, and the build
downloads that one file (512 KB) into the build directory. A submodule would
drag in the whole repository, whose pack file is 523 MB.

Re-pin by editing `FASTFLOWLM_COMMIT` and `XCLBIN_SHA256` together. The digest
is checked after every download, and a file whose digest does not match is
rebuilt rather than reused, so a stale build directory cannot mask a bad pin.

## What the sequence has to do

The overlay's instruction stream is normally generated by FastFlowLM's own
C++ harness. Three of its properties are not visible in the xclbin, and
`design.py` reproduces all three:

* **The cores read their shape from runtime parameters.** One overlay serves
  every GEMM in a model, so `K/512`, `M`, `N`, the activation and the clamp
  arrive as words at offset 4096 in each core's data memory, and a core blocks
  on lock 10 until the sequence releases it.
* **The shim channel map is fixed.** A arrives on MM2S channel 0 of columns 0,
  2, 4 and 6; B on MM2S channel 1 of *every* column; C leaves on S2MM channel
  0 of every column.
* **B arrives pre-packed**, in the order `pack_B` produces.

`FLMGEMM`'s own instruction stream does not drive this xclbin, even though the
two designs agree on tiling, on the byte order of every transfer and on the
packed B layout. It writes no runtime parameters, so the cores never start;
and its lowering puts B on MM2S channel 0 in the odd columns, which have no A
to share channel 0 with.

## Accuracy

Bit-identical to `FLMGEMM(rounding="floor")` at every shape measured — 256 /
512 / 1024, 512 / 1024 / 2048, 256 / 512 / 1536 and 1024 / 2560 / 2560 — and
for each of `silu`, `gelu`, `sigmoid` and a clamp, on both of `FLMGEMM`'s
`tile_n` settings. Each dispatch repeats identically.

The cores never leave the power-up rounding mode, so every bf16 conversion
truncates. The bias then accumulates over the K reduction instead of
cancelling, and it is entirely systematic: mean error and signed bias are the
same number. Against a fp32 CPU reference, as a fraction of the accumulated
mass `K * mean|A| * mean|B|`:

| | mean \|err\| | max \|err\| | bias |
|---|---|---|---|
| shipped overlay / `FLMGEMM` floor | 0.0098 | 0.0132 | **-0.0098** |
| `FLMGEMM` default (`conv_even`) | 0.00042 | 0.0028 | -0.00003 |
| `GEMM`, exact r=4 path | 0.0000004 | 0.0003 | -0.0000001 |

`FLMGEMM` in its default mode is *bit-identical* to `GEMM` at
`emulate_bf16_mmul_with_bfp16=True, prio_accuracy=True`, at every shape
measured: same mmul shape, same bfp16 emulation, same f32 accumulation, same
rounding.

`FLMGEMM` is the one to use for accuracy. This operator exists to measure the
shipped kernel, not to compute with it.

## Fixed geometry

`m/k/n = 64/512/128`, `r/s/t = 8/8/8`, on a 4x8 grid — the `GENERIC` build of
the design `FLMGEMM` was ported from. Hence `M % 256 == 0`, `K % 512 == 0`,
`N % 128 == 0`. `FLMGEMM` picks `tile_n` per shape and takes 64 whenever
`K > 512`; the overlay cannot, so the two run the same tiling only at `K = 512`.

## Performance

Min and median of 8 interleaved rounds, all three operators in one process,
`GEMM` at 8 columns and 64/64/64 tiles:

| M / K / N | `FLMGEMM` | shipped overlay | `GEMM` |
|---|---|---|---|
| 256 / 512 / 1024 | **166** / 182 us | 193 / 213 us | 199 / 216 us |
| 1024 / 2048 / 2048 | **1041** / 1118 us | 1079 / 1147 us | 3155 / 3236 us |
| 1024 / 2560 / 2560 | **1523** / 1602 us | 1827 / 1896 us | 4854 / 4914 us |

The port leads at every shape, by ~4% where it shares the overlay's `tile_n`
(K = 512) and by more where it does not.

Read `flm_gemm`'s README on how to measure this part before trusting a number
from it: dispatch latency is bimodal with modes ~6% apart, so configurations
have to be compared interleaved, as above, and a difference believed only when
the min and the median agree.
