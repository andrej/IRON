# xclbin Flow Investigation: workspace-0kn

## Summary

The xclbin-based IRON llama flow cannot produce correct output at 16 layers (full model)
due to an XRT firmware buffer object size limit. At smaller layer counts (1-5 layers),
the flow is architecturally correct but untested in this environment because no
xclbin-flow build artifacts exist.

## Key Findings

### 1. Different Compiler Flags Between Flows

The two flows use **fundamentally different compiler flags**, hardcoded in
`iron/common/compilation/base.py`:

| Flow | Flag | Line |
|------|------|------|
| ELF (default) | `--expand-load-pdis` | base.py:522 |
| xclbin | `--dynamic-objFifos` | base.py:566 |

These flags produce **different hardware partition layouts**:
- `--expand-load-pdis`: Better partitioning, ~6.5 tok/s
- `--dynamic-objFifos`: Different partitioning, ~4 tok/s

The issue description states both flows should use `--dynamic-objFifos`, but the current
code has them using different flags by design. The 6.5 tok/s advantage of the ELF flow
comes from `--expand-load-pdis`, not from the ELF dispatch mechanism.

### 2. Instruction Stream Size at 16 Layers

The xclbin flow embeds PDI data directly into the instruction binary via `patch_load_pdi`.
At 16 layers (compiled with `--expand-load-pdis`):

| Component | Size |
|-----------|------|
| Instruction binary (fused_op.bin) | 3.6 MiB |
| PDI data (42 .pdi files) | 885 KiB |
| **Total (instruction + embedded PDI)** | **4.5 MiB** |

The XRT firmware imposes a ~4 MiB limit on instruction buffer objects (bos). The 16-layer
instruction stream at 4.5 MiB **exceeds this limit**, causing timeouts.

Scaling by layer count:
- 2 layers: 770 KiB total (well within limit)
- 4 layers: 1.2 MiB total (within limit)
- 16 layers: 4.5 MiB total (**exceeds limit**)

### 3. No Pre-Built xclbin Artifacts

The xclbin flow has never been compiled on this system. All existing build artifacts
(`build_elf_{N}layers/`) were compiled with the ELF flow (`--expand-load-pdis`).
The xclbin flow requires:
- Individual operator xclbins (e.g., `RMSNorm_*.xclbin`) in `/workspace/build/`
- Fused operator xclbin + instruction binary compiled with `--dynamic-objFifos`

Neither exists. Running `--use-xclbin` fails immediately with "xclbin does not exist".

### 4. The `--elide-address-patches` Optimization Is Insufficient

Previous work (workspace-yuz, workspace-9if, workspace-gi0) implemented an optimization
to elide firmware address-patch instructions from the instruction stream. This saves only
~576 bytes — far too little to bring the 4.5 MiB stream under the ~4 MiB limit.

## Root Cause

The xclbin flow at 16 layers is **unfixable without firmware or XRT API changes**.
The instruction stream including embedded PDI data exceeds the firmware's buffer object
size limit. This is not a software bug in the IRON Python code — it's a fundamental
hardware/firmware constraint.

## Possible Solutions (All Require Significant Work)

1. **Split instruction stream across multiple bos**: Would require XRT API changes to
   support chained instruction buffer objects. This is a firmware-level feature.

2. **Stream PDI data separately**: Instead of embedding PDI binaries in the instruction
   stream, load them via a different mechanism. The ELF flow already does this implicitly
   (XRT handles ELF loading differently).

3. **Use `--expand-load-pdis` for both flows**: If the xclbin flow used `--expand-load-pdis`
   instead of `--dynamic-objFifos`, the instruction stream structure might differ, but the
   total size would be similar since the PDI data dominates.

4. **Reduce the number of PDI loads**: Compile with fewer hardware partitions to reduce
   the number of LOAD_PDI instructions and associated PDI data. This would require
   compiler changes.

## Recommendation

Close this issue as **won't fix** — the xclbin flow at 16 layers is blocked by a firmware
limitation. The ELF flow is the correct long-term solution and already works. A follow-up
issue should track "split instruction stream across multiple bos" for future firmware work.
